# St.NEA 新エージェント提案書

作成日：2026-07-09
ステータス：提案1は実装済み／提案2は方向性検討中

## 背景

St.NEAは、Web投稿記事のライティングとLINEスタンプ販売を事業とする仮想企業である。
現在は「編集部」に相当する7つのエージェントが `scripts/agents/` に実装されており、
`scripts/pipeline.py` が以下の業務フローを自動実行している。

```
Collector（収集）→ Validator（ファクトチェック）→ Legal（法務）→ Writer（執筆）
  → Publisher（サイト更新・メール配信）／ Archive（NG管理）／ Reporter（管理者通知）
```

既存事業（記事ライティング・LINEスタンプ販売）は変更しない前提で、
組織を拡張する2つの提案をまとめる。

---

## 提案1：編集長（Editor）エージェント【実装済み】

### 役割

Writerが書いたコラムを配信前にレビューする品質ゲート。
フローは「Validator → Legal → Writer → **Editor** → 配信」となる。

### チェック観点

1. フォーマット遵守（【タイトル】→ 📌リード文 → 本文 → 🔗ソース）
2. 文字数（タイトル30〜40字、本文200〜300字程度）
3. 禁止表現（「革命的」「ヤバい」「完全自動化」）の不使用
4. 断言を避けた表現（「〜とみられます」調）になっているか
5. 読者がすぐ試せるヒントが1つ含まれているか
6. 元記事からの逸脱・捏造がないか
7. 文末の「。」統一

### 判定ルール

| 判定 | 動作 |
|------|------|
| 問題なし | そのまま配信 |
| 軽微な問題（表現・体裁・文字数） | 編集長自身が推敲し、修正版を配信 |
| 修正不能な問題（捏造・元記事との重大な乖離） | 差し戻し。既存NGフロー（アーカイブ＋管理者通知）に接続し、修正可能として再キュー候補にする |
| APIエラー | フェイルオープン（レビューをスキップして配信を止めない。Validator/Legalと同方針） |

### 実装

- 新規：`scripts/agents/editor.py`（モデル：claude-sonnet-4-6）
- 変更：`scripts/pipeline.py` に `_write_and_edit()` を追加。通常配信と再キュー配信の両経路でEditorレビューを通す

## 提案2：社内開発チームの新設【方向性検討中】

### 結論

技術的に可能。エージェントの実体は「Claude APIを呼ぶPythonモジュール」なので、
チームの追加は「新しいパッケージ＋専用パイプライン＋専用スケジュール」の追加に等しく、
既存のコラム配信には手を触れずに共存できる。

### 構造案

```
scripts/
├── teams/
│   ├── editorial/     ← 既存の編集部（現 agents/ を移すか、そのまま残してもよい）
│   └── dev/           ← 新設の開発チーム
│       ├── planner.py     （PM：要件整理・タスク分解）
│       ├── engineer.py    （実装案・コード生成）
│       ├── reviewer.py    （コードレビュー・品質チェック）
│       └── pipeline.py    （開発チームの業務フロー）
```

- **共有するもの**：`config.py`（APIキー・SMTP）、`reporter.py`（管理者通知）、DB
- **分離するもの**：各チームのパイプラインとスケジュール（APSchedulerに別ジョブとして登録）
- 編集部の週次配信と並行して、開発チームは独自トリガー（週1の改善サイクル、または手動実行）で動かせる

### 開発チームの方向性（3案）

| 案 | 内容 | 備考 |
|----|------|------|
| A. 自社サイト改善 | index.html / dashboard.html の改修提案・実装 | エージェントが自らコミットする仕組みが必要。GitHub書き込み権限の解決が前提 |
| B. LINEスタンプ事業支援 | スタンプ企画・キャッチコピー・審査ガイドラインチェック | 既存と同じ「テキスト生成＋チェック」型。現行の仕組みのまま実装可能 |
| C. パイプライン保守・改善 | NG率の分析から設定チューニング案を提案 | 既存DBの実績データを活用 |

### 次のステップ

1. 開発チームの方向性（A/B/C）を決定する
2. 決定した方向性に合わせてチーム構成（エージェントの顔ぶれ）と業務フローを設計する
3. `scripts/teams/dev/` として実装し、スケジューラに登録する
